# node-check

Диагностика ноды Xray / Remnawave одной командой и автотюнинг сети под VPN-трафик: BBR, fq, буферы, очереди, conntrack.

Скрипт собирает короткий отчёт о состоянии сервера, сохраняет его в файл и, если BBR или fq не включены, сам включает их вместе с оптимизацией под скорость и стабильность.

## Быстрый старт

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/WeaveProduct/node-check/main/node-check.sh)
```

Только посмотреть, ничего не меняя:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/WeaveProduct/node-check/main/node-check.sh) --dry-run
```

Нужны права root. Рассчитан на Ubuntu и Debian с systemd.

## Режимы

| Команда | Что делает |
|---|---|
| без флагов | отчёт; если BBR или fq не включены, включает их и применяет тюнинг |
| `--dry-run` | только отчёт, на сервере ничего не меняется |
| `--fix` | применить тюнинг, даже если BBR уже включён |
| `--no-speed` | пропустить спидтест (~15 секунд вместо минуты) |

Флаги можно комбинировать: `--fix --no-speed`.

## Что проверяется

| Раздел | Что смотрит |
|---|---|
| Система | ОС, ядро, виртуализация, CPU, аптайм, load average |
| Память и диск | RAM, swap, свободное место, размер Docker-логов |
| CPU steal | `vmstat`: если `st` стабильно выше 5–10%, хостер перепродаёт CPU |
| TCP / BBR | congestion control, qdisc по умолчанию и **фактический** qdisc на внешнем интерфейсе, MTU |
| Sysctl | буферы, очереди, fastopen, MTU probing, conntrack |
| Соединения | `ss -s`, кто слушает 443 и 80 |
| Docker | контейнеры, их CPU и RAM, ошибки `remnanode` (без шума от ежедневного рестарта Xray) |
| Пинг | 1.1.1.1, 8.8.8.8, 77.88.8.8 (Яндекс): задержка и потери |
| Спидтест | скорость загрузки и отдачи сервера |

Отчёт сохраняется в `/root/node-report-<хост>-<дата>.txt`.

## Что меняет тюнинг

Все настройки пишутся в отдельный файл `/etc/sysctl.d/99-xray-tuning.conf`. Существующий файл с тем же именем сохраняется как `.bak.<timestamp>`. Перезагрузка не нужна: новые соединения сразу идут с новыми параметрами.

| Параметр | Значение | Зачем |
|---|---|---|
| `tcp_congestion_control` | `bbr` | держит скорость на маршрутах с потерями, в отличие от `cubic` |
| `default_qdisc` + qdisc интерфейса | `fq` | BBR рассчитан на работу с fq, без него хуже |
| `rmem_max` / `wmem_max`, `tcp_rmem` / `tcp_wmem` | до 16 МБ | полная скорость на длинных маршрутах |
| `somaxconn`, `netdev_max_backlog`, `tcp_max_syn_backlog` | 8192 / 16384 / 8192 | без потерь при пиках подключений |
| `tcp_mtu_probing` | `1` | обход «чёрных дыр» MTU, частых в мобильных сетях |
| `tcp_slow_start_after_idle` | `0` | нет просадки скорости после пауз |
| `tcp_notsent_lowat` | `16384` | ниже задержка в интерактивном трафике |
| `tcp_fastopen` | `3` | быстрее установка соединений |
| `tcp_fin_timeout`, keepalive, `tcp_tw_reuse` | 15 с / 300 с | быстрее освобождаются мёртвые соединения |
| `ip_local_port_range` | `10240 65535` | больше исходящих портов |
| `nf_conntrack_max` | по объёму RAM (64K–1M) | таблица соединений не переполняется |
| `fs.file-max`, `DefaultLimitNOFILE` | 1048576 | лимит открытых файлов для Xray и Docker |

Если ядро не поддерживает BBR (нужно 4.9+ с модулем `tcp_bbr`), скрипт применяет остальной тюнинг без него и сообщает об этом.

## Откат

```bash
rm /etc/sysctl.d/99-xray-tuning.conf /etc/systemd/system.conf.d/99-nofile.conf
sysctl --system
```

## Как читать отчёт

- **`congestion_control: cubic`** или **qdisc `pfifo_fast` / `fq_codel`**: тюнинг не применялся, запустите без `--dry-run`.
- **`st` в vmstat стабильно выше 5–10%**: виноват хостер, тюнинг не поможет.
- **`table full` в разделе conntrack**: таблица переполнялась, тюнинг увеличит её размер.
- **Диск занят больше чем на 90%**: часто это логи Docker. Ограничьте их через `log-opts` в `/etc/docker/daemon.json`.
- **Потери пакетов при пинге**: проблема в сети хостера или аплинке.
- **Сервер в норме, а клиенты жалуются**: проблема, скорее всего, на маршруте клиента или у его провайдера. Попросите клиента прогнать `mtr` до IP сервера.
